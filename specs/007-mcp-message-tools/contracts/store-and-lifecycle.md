# Internal Contract: Bounded Message Reads

## Ownership and Work Budgets

Use the existing `ToolReader` admission and a single read-only snapshot per admitted tool call. The handler passes validated selectors and a narrow, synchronous reply-sizing policy, not SQL, a connection, or a write/account capability. The store owns the work ledger; the MCP boundary owns escaping, DTO policy and wire accounting. The sizing policy must not serialize, do I/O, spawn work, retain rejected records, or reenter the store. Its retained output consists only of the admitted reply and fixed scratch. Do not return a lazy iterator to the caller or hold a snapshot during output writes.

| Boundary | Ceiling and enforcement |
| --- | --- |
| Admission and lifetime | Reuse 006: 4 protocol requests and 1 tool; 16 active store operations and 4 reader connections. Keep the ordinary waiter cap of 64 (65 while a tool holds a slot), with zero tool waiters. Request store cancellation within 5 s and tool cancellation within 10 s; public output wait is at most 5 s or earlier cancellation. Keep resources charged until actual return, including under cancellation. |
| WAL and disk | Preserve 006's no-ordinary-waiter admission, WAL/checkpoint and transaction fence. Admit at or below 64 MiB WAL using the stable writer observation and fresh free-space sample of at least 640 MiB; refuse failed measurement. Keep cancellation/drain above 128 MiB WAL and the existing rate-limited recovery checkpoint, with no new writer path. |
| Search candidate walk | At most 400,001 candidate visits per call and 256 keys per first-step batch; see [feasibility evidence](../feasibility.md). Count discarded offset matches, alias lookahead, duplicates and terminal probes that return keys. Keep at most two buffered streams and 200 retained page keys. Refill with the lesser of 256 and the remaining visit budget. Length-check each chat address and ID at 256 bytes before copying into intermediate keys; malformed rows fail closed. |
| Text search | At most 80 MiB original and 320 MiB folded bytes per call. Before materialization or matching, validate lengths with checked arithmetic and debit both ledgers. A source field is at most 256 KiB, its stored fold at most 2,621,440 bytes on the pinned Unicode tables. Evaluate only admitted rows of a bounded batch; retain keys and match flags, not a batch of text bodies. Reject malformed legacy data without disclosure and never count work exhaustion as a non-match. |
| Non-search lookup | Exact pair and bounded name/alias lookups by indexed equality. For ID-only, seek up to 101 keys without sorting the matching range; sort the bounded list only when at most 100 keys were found. Last interaction uses up to two direct seeks and up to two ordered sender streams. Check residual group and authored-by-contact rules *after* candidate enumeration, with the same visit ceiling; never return a direct candidate if an unfinished group stream can beat it. Own aliases skip group scanning. |
| Context and result reads | Cap at 20 returned neighbours per side and 2,000 context row touches across the request. Reserve a row credit before each indexed one-key probe or point projection. Charge each positive probe and each row fetched for projection separately, even when its body is rejected; refund a reservation only for work that did not touch a row (for example, a probe that found no key). Charge 32 MiB cumulative result-field materialization, including data considered and dropped or previewed; search-fold probes use the separate work ledger above. Check lengths, type and UTF-8 before retaining a projection. Keep one bounded scratch projection and reserve capacity for first-anchor/edge metadata. |
| Reply | Existing 2 MiB structured, 2 MiB text, and 8 MiB total wire-frame ceilings. Reserve markers, separators and outer envelope up front. Charge escaped fields before accumulating rows; cross-check actual encoded bytes and wire frame. The actual response limit is not enlarged to fit a preview. |

## Query and Assembly Order

1. Select global, chat, sender or chat/sender time index according to the filters, with ordered tuple seeks and exact date bounds. Validate the generated plan for every shape, including continuations, ties and alias branches. Do not allow a SQL sort or filter over unbounded input before the candidate limit. Folded evaluation and other residual filters happen only on enumerated keys. All substantial statements, including bounded batch aggregation, do their expensive work in the monitored first step; avoid cancellation-dependent late iteration.
2. Confirm the requested page, exact identity, or latest qualifying key in the snapshot. Count full-page membership without fetching all selected bodies. If a bound prevents verification, return the typed work-limit outcome without data. A full page does not require a peek beyond its final match; a short result requires proven exhaustion. All work shares the same lease and deadline.
3. Materialize base anchors in order, one at a time. For a context-enabled prefix, stop at the first complete anchor that will not fit. If that is the first anchor, shorten only its text/caption on rune boundaries; a fixed fallback of at most 32 KiB per field leaves ample escaping headroom once validated against the actual encoder. Reserve a worst-case summary and reduction flags before admitting any anchor. If context is off, keep the complete page requirement.
4. Before expanding any retained anchor, reserve and run one same-chat indexed nearest-key probe per non-zero side (at most 400 initial probes). Each side then has either a known next key or a proven end. Walk anchors newest first and alternate sides within each anchor (before first). To try a known key, reserve its projection and, unless it is the final requested neighbour on that side, a successor probe before projecting it. If those credits cannot be reserved or the projection will not fit, stop that side and mark it reduced using the known unreturned key; do not look past it. If the projection fits, use the reserved successor probe with a strict timestamp/ID boundary before publishing the neighbour. Advance using the returned key or record the proven end; do not probe past the requested count. An empty or fulfilled side is never marked reduced. Propagate storage errors and cancellation instead of treating them as exhaustion. Publish both arrays chronologically. No lookup or probe for discarded anchors.
5. Return statements, transaction and connection before final encoding. Use the existing tool-error and mandatory redacted reporting paths. Errors do not disclose unverified keys, secrets or raw SQL. Over-cap, cancellation, transport abandonment, reporting failure and shutdown do not release the store/owner early or start replacement work.

## Pre-Implementation Evidence Gate

Before enabling these query shapes, complete the [feasibility record](../feasibility.md) and obtain a current design PASS covering it. Run scratch work outside `/speckit-implement`. Record actual seek plans and examined rows/bytes for sparse, deep, tied, alias, grouped and max-field fixtures. Demonstrate checked byte arithmetic, bounded retained projections and ephemeral allocations (including SQLite heap/cache/temporary structures, Go and SDK copies), pre-materialization field guards and actual driver cancellation through connection return. Fit the existing 32 MiB tool SQLite heap share within the process-wide 256 MiB SQLite limit. Test held-reader interference and return/fence ordering. If any required fixture fails, revise the design under review rather than silently narrowing the search window or weakening an inherited control.
