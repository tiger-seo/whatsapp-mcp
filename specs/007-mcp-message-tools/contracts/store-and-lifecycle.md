# Internal Contract: Bounded Message Reads

## Ownership and Work Budgets

Use the existing `ToolReader` admission and a single read-only snapshot per admitted tool call. The handler passes validated selectors and a narrow, synchronous reply-sizing policy, not SQL, a connection, or a write/account capability. The store owns the work ledger; the MCP boundary owns escaping, DTO policy and wire accounting. The sizing policy must not serialize, do I/O, spawn work, retain rejected records, or reenter the store. Its retained output consists only of the admitted reply and fixed scratch. Do not return a lazy iterator to the caller or hold a snapshot during output writes.

| Boundary | Ceiling and enforcement |
| --- | --- |
| Admission and lifetime | Reuse 006: 4 protocol requests and 1 tool; 16 active store operations and 4 reader connections. Keep the ordinary waiter cap of 64 (65 while a tool holds a slot), with zero tool waiters. Request store cancellation within 5 s and tool cancellation within 10 s; public output wait is at most 5 s or earlier cancellation. Keep resources charged until actual return, including under cancellation. |
| WAL and disk | Preserve 006's no-ordinary-waiter admission, WAL/checkpoint and transaction fence. Admit at or below 64 MiB WAL using the stable writer observation and fresh free-space sample of at least 640 MiB; refuse failed measurement. Keep cancellation/drain above 128 MiB WAL and the existing rate-limited recovery checkpoint, with no new writer path. |
| Search candidate walk | Up to 100,200 visits per call, including discarded offset matches, alias lookahead, duplicates and terminal probes that return keys. Up to 64 keys in one indexed batch, at most two buffered streams, and at most 200 retained page keys. These are proposed design ceilings, not measured compatibility claims. Request no overshoot batch; use smaller initial/refill batches to avoid consuming out-of-order work on small lookups. |
| Text search | When a text predicate is active, validate source lengths before materialization and debit 64 MiB cumulative original content/caption length and 256 MiB cumulative folded bytes; read no more than one candidate's checked fields at a time. Use the existing stored folds and query folding; demonstrate a finite per-field expansion bound against the pinned folder and refuse malformed legacy fields. Do not turn exhaustion into a non-match. |
| Non-search lookup | Exact pair and bounded name/alias lookups by indexed equality; cap ID-only at 101 keys. Last interaction uses up to two direct seeks and up to two ordered sender streams. Check residual group and authored-by-contact rules *after* candidate enumeration, with the same visit ceiling; never return a direct candidate if an unfinished group stream can beat it. Own aliases skip group scanning. |
| Context and result reads | Cap at 20 neighbours per side and 2,000 context rows touched across the request, including positive presence probes and rejected materializations. Charge 32 MiB cumulative result-field materialization, including data considered and dropped or previewed; search-fold probes use the separate work ledger above. Check lengths, type and UTF-8 before retaining a projection. Keep one bounded scratch projection and reserve capacity for first-anchor/edge metadata. |
| Reply | Existing 2 MiB structured, 2 MiB text, and 8 MiB total wire-frame ceilings. Reserve markers, separators and outer envelope up front. Charge escaped fields before accumulating rows; cross-check actual encoded bytes and wire frame. The actual response limit is not enlarged to fit a preview. |

## Query and Assembly Order

1. Select global, chat, sender or chat/sender time index according to the filters, with ordered tuple seeks and exact date bounds. Validate the generated plan for every shape, including continuations, ties and alias branches. Do not allow a SQL sort or filter over unbounded input before the candidate limit. Folded evaluation and other residual filters happen only on enumerated keys. All substantial statements, including bounded batch aggregation, do their expensive work in the monitored first step; avoid cancellation-dependent late iteration.
2. Confirm the requested page, exact identity, or latest qualifying key in the snapshot. Count full-page membership without fetching all selected bodies. If a bound prevents verification, return the typed work-limit outcome without data. A full page does not require a peek beyond its final match; a short result requires proven exhaustion. All work shares the same lease and deadline.
3. Materialize base anchors in order, one at a time. For a context-enabled prefix, stop at the first complete anchor that will not fit. If that is the first anchor, shorten only its text/caption on rune boundaries; a fixed fallback of at most 32 KiB per field leaves ample escaping headroom once validated against the actual encoder. Reserve a worst-case summary and reduction flags before admitting any anchor. If context is off, keep the complete page requirement.
4. For retained anchors, establish availability for each non-zero side with a same-chat indexed nearest-key probe, reserving this edge accounting within the context budget before expanding. Reuse probed keys, not duplicate reads. Walk anchors newest first; within each anchor try neighbours in increasing distance by taking the nearest on each side in alternating order (before first at equal distance). Stop each side when its nearest remaining message will not fit; do not substitute a farther neighbour. An omitted available neighbour sets the corresponding flag even when no neighbour body was read. Publish both arrays chronologically. No lookup or probe for discarded anchors.
5. Return statements, transaction and connection before final encoding. Use the existing tool-error and mandatory redacted reporting paths. Errors do not disclose unverified keys, secrets or raw SQL. Over-cap, cancellation, transport abandonment, reporting failure and shutdown do not release the store/owner early or start replacement work.

## Pre-Implementation Evidence Gate

Before enabling these query shapes, require a reproducible synthetic feasibility check and owner design review. Record actual seek plans and examined rows/bytes for sparse, deep, tied, alias, grouped and max-field fixtures. Demonstrate checked byte arithmetic, bounded retained projections and ephemeral allocations (including SQLite heap/cache/temporary structures, Go and SDK copies), pre-materialization field guards and actual driver cancellation from first step through connection return. Fit the existing 32 MiB tool SQLite heap share within the process-wide 256 MiB SQLite limit; the logical byte caps are not live heap allowances. Test a held reader against ordinary and device writers and verify the same return/fence ordering. If any index cannot bound work, or the 50-match fixture cannot complete under existing limits, block implementation and revise the design under review; no raw-store-limit fallback or broader exception is granted.
