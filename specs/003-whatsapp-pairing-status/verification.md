## Repair Controller (T036-T038) - 2026-11-06

**Code.** `internal/wa/recovery.go` adds `repairController`: after a confirmed connection it recovers each pending collection once per generation with a real full `FetchAppState`, behind an owner-wide actual-call slot that is released only when the invocation returns. The caller waits at most ten seconds (`repairDeadline`); a timeout, failure or write fault cancels the ticket and keeps the marker; a late success is discarded; a busy slot starts no replacement call and does not spend the collection's budget. Clearing goes through the store's fenced `CompleteRepair`. Once no marker remains, coalesced deferred demand is replayed incrementally through the same slot, one call per collection, with no autonomous retry. `Session.RunRepairs` wires the real `client.FetchAppState`; `connectionOwner.startRepair` starts one pass per generation on the first `Connected` event, `retireGeneration` joins it, and `Health().RecoveryPending` follows the session. `SessionConfig.RepairSlot` is the shared slot. Admission (untagged app-state progress, MAC and bulk work rejected while recovery is pending, tagged repair and key delivery allowed) already existed in the store and was not changed.

## Version Discovery Failure: Cause and Fix - 2026-11-06

**Symptom.** Both real pair runs logged `version discovery failed; keeping the last usable version` and used the bundled version `2.3000.1050728964`. The log gave no cause.

**Cause.** The discovery request sent only a `User-Agent`. A plain `GET https://web.whatsapp.com` (curl, default headers) returned HTTP 200 and a 40 KB page without `"client_revision":N,`; the revision appeared only as `data-btmanifest="1053473644_main"`. The same request with the pinned SDK's own navigation headers (`Sec-Fetch-Dest/Mode/Site/User`, `Accept`, `Accept-Language`), run by the user in their terminal, returned HTTP 200 and a 927 KB page containing `"client_revision":1053473644,`. So every refresh ended in `ErrVersionResponse`. A second probe with only our User-Agent was blocked by the tool classifier and not retried, so that exact request shape was inferred, not observed.

**Fix.** `internal/wa/version.go` now sends the same navigation headers as the pinned SDK. The two `version_refresh_failed` warnings carry `reason=fetch|response|other` (category only, never response content). Tests: `TestVersionRequestLooksLikeANavigation` and `TestVersionFailureReasonNamesTheCategoryOnly` (the build failed before the fix because `versionFailureReason` did not exist). `go vet ./internal/wa` clean; `go test ./internal/wa ./internal/wasim ./cmd/...` pass (wa 13.4 s, cmd 129.2 s).

**Not verified.** That the shipped binary now selects `2.3000.1053473644` against the real server, and that the handshake accepts the refreshed version. The next real run shows it in the log (no `version_refresh_failed`) and `status` should then report a refreshed version. The refreshed value is also what the live handshake sends, so a rejected version would surface as a 405.

**Safety flow (all before any side effect).** The directory must be absolute and must not be the default data directory (compared case-insensitively on Windows and macOS); the action must be `connect` or `pair`; stdin and stdout must be an interactive terminal (character devices); the exact action, directory and effect are printed; then a typed approval `I permit <action> in <directory name>` is read through one bounded reader (256-byte lines, an oversized line is rejected whole). **Denial check (`-denial`).** After the observation, and only after a second typed approval `I permit the denial check`, it asks for a pairing window once more in the same process. A refusal (`ErrUnsafeRun`, `ErrAlreadyPaired`, `ErrStopping`) prints `denial confirmed`; an accepted request is a failure (exit 1), the window is cancelled at once and `NOT denied` is printed.
