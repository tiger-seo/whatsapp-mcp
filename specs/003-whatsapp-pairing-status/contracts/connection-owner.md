# Contract: Connection Owner and Offline Substitutes

**Scope**: Internal Go boundary for feature 003 and later adapters. No MCP tool, HTTP endpoint or new CLI command is exposed here. Use pinned WhatsApp domain/protobuf types where appropriate; this document specifies obligations without complete implementation bodies.

## Public Capability Surface

| Capability | Contract |
| --- | --- |
| Lifecycle | Start(ctx) creates the one owner and selects a version; reconnect an existing saved identity, otherwise remain unpaired without Connect/QR until an explicit request. BeginStop/Done distinguish stop requested from quiescence completed. |
| Status | Snapshot() returns a copied coherent four-field status; no I/O or pairing side effect. |
| Pairing | RequestPairing(ctx) explicitly authorizes a window or shares an existing one; return copied current-code/state, not the raw upstream channel. CancelPairing is explicit. Already-paired, pending, expired/failed and stopping outcomes are distinguishable. |
| Events | Subscribe/register through a narrow owner interface; current epoch is checked before mutation and stale callbacks are denied. No raw client handle is handed to consumers. |
| Health | Internal device-data readiness/recovery-pending/fault state, separate from login fields. Later contact-dependent tools must check it; no extra login-schema field is invented. |
| Future services | Narrow Sender, Uploader, Downloader, ContactLookup and GroupLookup interfaces. Fake implements all with in-memory responses. Real tool routing/sends/media remain disabled in 003; unsupported calls fail explicitly. |

Mirror SendMessage(ctx,JID,*Message), Upload(ctx,bytes,MediaType), GetUserInfo(ctx,[]JID) and GetGroupInfo(ctx,JID) through narrow subsets of the pin, not the whole client. Future download must support persisted metadata rather than assume feature 002 stored an original full message. Types/signatures are compile-checked against the pin during implementation; changing the pin requires re-audit. Fake results/fixtures must not alias mutable state across calls or contact a network.

Concretely, Downloader declares `DownloadMedia(ctx context.Context, kind whatsmeow.MediaType, meta store.MediaMeta) ([]byte, error)`, using the persisted metadata type in internal/store/messages.go (including nullable FileLength), not DownloadAny's full-message input. Sender keeps the pin's SendRequestExtra/SendResponse shape; Uploader keeps UploadResponse; ContactLookup and GroupLookup use the pin's JID/UserInfo/GroupInfo types. These are declared/tested with the fake in 003; real send/upload/download routing remains disabled until its roadmap feature applies its own limits.

## Protocol Adapter and State

- Construct from the locked/open shared store; load/wrap device before NewClient. No second database or raw storage outside internal/store.
- Set options and log bridge before Connect. Default deny all automatic reconnect, including upstream-initiated reconnect, until the particular path meets the proof and review gate below; the existing `EnableAutoReconnect=true` implementation is not evidence of compliance. `InitialAutoReconnect=false` and `DisableLoginAutoReconnect=true` do not by themselves establish that denial. A post-error `AutoReconnectHook`, lifetime cancellation or expected-disconnect alone is not proof of pre-connect exclusion. Do not assume an unsupported upstream interception or join mechanism exists.
- Set BackgroundEventCtx to the generation lifetime before client use, not the temporary load/operation/watchdog context. Configure pending-repair admission before NewClient/Connect so SDK background sync cannot race ahead of the controller.
- One owner-initiated connection attempt in flight, including initial, explicit, startup-retry, 405 and 515 connects. Start a separate 30-second watchdog for each, independently of the generation lifetime; disarm on valid initial pairing QR or current Connected. On timeout flag termination, cancel first, then Disconnect and drain; retain the attempt slot until the call and generation access drain. A successful connection must survive the old watchdog deadline.
- Saved-session startup retains its desired budget of at most three further attempts after cancellable five-second waits, subject to the restriction below. Connected, shutdown, logout, storage fault or 405 handoff ends the sequence; 405 uses only its own budget. Exhaustion or unavailable recovery retains identity, stays disconnected, reports the reason and starts no pairing. `pair` retains its failure exit.
- Startup retries, 405, 515 and ordinary pinned reconnect are denied by default. Each may be enabled only after demonstrating that its actual upstream and owner execution stays in the same active generation and remains safe in the presence of work detached by earlier connections, and after the applicable current owner review and implementation/evidence gates pass. Never start another Connect on or after retirement of an unproven upstream generation, including a replacement client. Otherwise the affected path is temporarily unavailable and reports that limitation. Reset the desired 405 budget only on current Connected, not refresh success or a stale event; neither its counter nor an unsafe marker proves retry safety.
- GetQRChannel occurs before Connect; one dedicated consumer reads it promptly for the whole attempt. Do not stop draining when one requester cancels. Window lifetime belongs to owner approval/upstream terminal state, not a returned request context.
- For fresh QR registration, use per-client Chrome QR type and cloned companion properties identifying OS `Linux` and platform `CHROME`; keep their version and the cloned user-agent OS version/build consistent with the selected handshake triple. Do not mutate shared library globals or change saved identity; the exact phone label is controlled by WhatsApp and is not guaranteed.
- Before a new logical window, retire/drain the old client and reload saved identity to avoid overwriting it; after any production Connect attempt no new same-process pairing window is permitted. A late identity is not reusable until FR-018 offline recovery. A 405 retry inside a still-approved window remains subject to the same-active-generation safety condition; final timeout/cancel cannot automatically open another.
- PairSuccess clears QR and records durable identity; command success still needs Connected. On logout clear status immediately and schedule retirement outside event-handler locks. Remove/drain old access and persist revocation before a fresh device can be constructed.
- A post-pair 515 may require a further connection to reach Connected; it is not established that every pairing receives 515. Until T077's path-specific proof and applicable review permit that reconnect, deny it, report that linking could not be completed safely and offline recovery is required, and exit unsuccessfully without claiming the identity is connected or usable. Retain unsafe, drain normally and do not open another pairing window.
- Do not remove identity for ordinary disconnect, invalid version response or failed retry. If revocation cleanup cannot persist, block new account work/generations and report failure, never re-pair success. Explicit stop still finalizes after true quiescence with an unsuccessful result and unresolved-state warning.
- Under the store lock, durably arm before account-capable work. Arm failure or ambiguity admits no account work. Any production Connect attempt, including failed or cancelled, requires retaining unsafe even after orderly drain and logout cleanup; only separately authorized offline recovery may clear it subsequently. Without an attempt, clear only after true drain and durable cleanup. Ambiguous clear exits unsuccessfully and requires committed-state inspection. Unsafe/unknown/invalid state blocks automatic Connect, pairing and QR even without a device row. Drain resources and release the lock only after quiescence regardless of marker state.
- Set the invocation's attempted-Connect latch immediately before calling the upstream production Connect boundary, after durable arm succeeds and before the call may block, fail or observe cancellation. A pre-boundary rejection is not an attempt; no return outcome clears the latch. T075/T076 own runtime tests and implementation.
- An opened fresh-pair window that times out, fails, is cancelled or is stopped before both durable identity and current-generation Connected remains unresolved even after orderly drain; retain the unsafe marker and require offline recovery. PairSuccess or the absence of a local row alone cannot prove that no phone-side link exists.
- Recovery from unsafe/legacy-unknown state is offline and explicitly interactive in `pair`, not automatic or implied by Enter. The operator verifies the named account/device, separately authorizes any needed phone-side unlink and local identity removal, and separately approves any later fresh pairing. Keep chats/messages, do not infer revocation from the marker, do not offer reuse of the uncertain identity, and preserve the block on refusal, EOF, unverifiable phone state or definite failed persistence. An ambiguous commit requires reopening to inspect committed state before further action. See the CLI contract for exit/status behavior.
- A logout or deferred deletion recognized before callback/device admission drains is latched across retirement. Cleanup must be durable; failure retains unsafe. No post-attempt shutdown clear is permitted even after cleanup. An event never recognized before admission closes is not claimed observed. Test the real callback, guarded delete, shutdown and SQLite marker with deterministic race barriers.
- The existing disk gate and its 256/512 MiB hysteresis apply to cleanup and marker clear without exemption. A refused clear leaves unsafe state and an actionable free-space/offline-recovery diagnostic. Platform-specific synchronization and conditional Darwin durability follow the plan; a process-kill test is not power-loss evidence.

QR-only invariant: never call/expose SendPasskeyResponse or PairPhone. The pin's QR channel has a SkipHandoffUX auto-confirm branch, so merely ignoring an output item is not a prevention mechanism. At this pin the linking cache is armed only by SendPasskeyResponse; an unarmed client rejects continuation/confirmation before sending IQ (pair-passkey.go:166-168,211-216). Keep that invariant for every new client and test the real channel path with synthetic DispatchEvent through the pin's test-only DangerousInternals, a forbidden-network transport and an unarmed cache. Reject the resulting unsupported/error state safely. Do not call DangerousInternals in production or claim the branch was tested using only a fake QR consumer; re-audit this guard on a pin change.

### Reconnect Proof Gate

Before enabling each automatic path, specify the actual supported mechanism and its coverage at the pinned dependency; if exclusion or safe handling of detached upstream work cannot be established, keep the path disabled. With synthetic identities, isolated SQLite and denying transports, use deterministic barriers to hold an earlier connection's actual pinned node handler and asynchronous logout/delete dispatch across disconnect and the proposed retry, including a second reconnect, timeout/cancellation, retirement and stop. Exercise the real owner callback and guarded device store: verify old work cannot incorrectly change the new connection's identity/status, cause an unrecorded revocation or permit unsafe marker clearing, a late delete is safely handled or blocks further work, and no overlapping or post-retirement Connect occurs. Assert attempted connection counts at the actual transport/adapter boundary, preserved chat and repair sentinels, and no database close or lock release while admitted work remains. Include both the default-denied path and any candidate enabled path; use controlled barriers rather than timing sleeps. A fake callback alone, marker retention, retry budget, queue waiter or a successful Disconnect does not establish the required upstream coverage. Record source-level coverage, runtime results and limits separately; no finite synthetic matrix proves every upstream schedule.

Fresh design PASS is required before implementation resumes. Before enabling a path, obtain an applicable current owner review of its supported mechanism and deterministic evidence, resolve any BLOCK or owner-decided CONCERNS, and satisfy all other applicable safety, native-platform, exception and code-review gates; do not treat the review or these tests as account permission. If the mechanism requires an unapproved dependency change, fork or new product decision, stop for the user's separate decision. No prior review or historical test establishes this proof.

## Versions and Discovery

The provider exposes immutable bundled/selected version values and one shared in-flight refresh. A waiting caller's cancellation does not create a parallel request or silently cancel another caller's owner-managed refresh. Owner stop cancels the actual request.

Callback requirements: clone fresh default device payload; snapshot candidate once; patch AppVersion, user-agent OS version/build, registration BuildHash and the specified cloned companion identification properties, leaving all other fields, protobuf unknown fields, keys and identifiers intact. Mutate existing cloned nested version fields rather than replacing messages, allocating only if absent. On companion-property decode/encode failure return nil so the pinned handshake rejects the payload and preserve credentials; never send an unmodified or partially modified registration or panic. Record coalesced category bits before a nonblocking wakeup, with a generation-lifetime consumer that emits fixed secret-free diagnostics outside the callback and drains pending bits on orderly retirement; a full wakeup cannot erase a pending category. Repeated identical failures may coalesce, and forced termination or an indefinitely stalled logger cannot guarantee delivery. No SetWAVersion/SetOSInfo/global mutation, locks acquired under socketLock, network or SQL. A refresh may update next-handshake candidate while a socket stays connected. The bundled offline-status version remains available without provider startup.

Discovery requires fixed secure origin, certificate verification, redirects rejected, 15 seconds and at most 1 MiB consumed application body. Reject advertised oversize before reads and unknown-length responses that exhaust the budget without completion; never accept a truncated revision prefix. Preserve the prior candidate, emit safe category-only warning. Accept decimal revision representable by uint32, including zero, with fixed pinned major/minor. No credentials, response body or arbitrary upstream text in error output.

## Device Store API and Admission

Proposed Store additions live in internal/store:

| API | Obligation |
| --- | --- |
| Inspect(ctx,dataDir) | Read-only committed-view snapshot of saved identity; no writable Open, upgrades, migrations or new device. Caller owns present storage; missing-artifact path does no database read. |
| LoadDevice(ctx) | Load/create through shared admission/disk readiness; publish stable guarded fields before client creation, never raw stores. Interface wiring is Initialized before exposure; private delegates bind once on validated JID. Save-readiness, not Initialized, proves persistence. No second live session until retirement and no exported raw container. |
| DeviceBarrier.Retire(ctx), Done | Reject new old-generation access, drain admitted work; timeout cannot imply Done. Does not close the shared store for future pairing. |
| Quiesce(ctx), Quiesced | Permanently close shared admission, cancel/drain using existing profile. Completion signal means zero active operations, not merely grace elapsed. |
| Close(ctx) | Return not-quiescent without closing pools while active; set closed only after true drain/pool close. Retry/finalize after completion with live cleanup context. |
| PendingRepairs / BeginRepair / CompleteRepair | At most five known collections for the owned device; bounded validated rows and ticket-fenced clear as in data-model.md. No external repair endpoint. |
| Controlled revoked-device removal | After old-client drain, remove only the confirmed revoked local device through admitted maintenance; never application chat/message tables or a phone-side unlink. |

Store retains the same dbutil.Database supplied to NewWithWrappedDB. Raw vendor delegates and custom contact/LID operations preserve its transaction key. DoDecryptionTxn owns one lease; nested compatible operations preserve values/deadline/cancellation without re-admission or another writer. Reject incompatible nested bulk/marker work before mutation rather than deadlock. Do not embed raw interfaces in a way that silently promotes a future unguarded method.

Stable first-Save path: create private SQLStore delegates once JID is valid, keep device fields pointing to guards, and skip raw container initialization by completing interface wiring before client use. Ordinary pre-ready calls fail fast before admission/SQL; they cannot occupy every slot while Save waits for admission. Readiness is signalled only after durable Save. Preserve this on error, cancellation and late completion; a final pointer check after temporary raw publication is not a sufficient test.

Client Container.DeleteDevice requests/coalesces retirement and returns typed deferred cleanup, preventing the SDK's successful ID/LID/Deleted/Noop-store rewrite. Owner-controlled confirmed-revocation SQL removal follows drain via private container/shared admission. Failure blocks account work/new generations and never reports cleanup success. Explicit shutdown must still finish once writes are quiescent, close/unlock and exit unsuccessfully, retaining the armed unsafe-run marker and warning that offline recovery is required; it must not wait forever solely for failed deletion after drain. Ordinary pairing errors preserve durable identity. No account command or remote unlink is added.

All guarded calls validate before their own writes, use shared admission/deadline/disk classification and return safe errors. No whole-sync rollback is promised: later policy errors can follow earlier sibling commits. Existing message-count caps do not silently truncate address books; aggregate typed input and bounded SQL batches govern bulk contacts. Device GetAllContacts/GetAllAppStateSyncKeys are explicitly unsupported/resource-limited in 003; later application tools use bounded store queries. Use a cache-less MigratePNToLID implementation, preserving its transactional session-migration semantics without raw SQLStore.migratedPNSessionsCache. Do not classify a store-resident cache as excepted receive work merely because traffic populates it.

## Durable Recovery Protocol

1. Commit a dirty marker before each protected version/MAC/bulk-contact mutation; fail before mutation if the marker cannot be recorded. Marker input is validated before either write. Partial commit is visible and recoverable, not called corruption-free atomic whole-sync completion.
2. Following an authorized connection, one worker reads startup/fault-pending collections and performs at most one automatic full-resync per collection per owner generation, using the existing API and ten-second context. No gate lease or SQL transaction across network I/O. App-state HTTP body/deadline use the approved reused 16-MiB/ten-second profile and reject redirects/truncated responses.
3. Repair receives a unique ticket. Guarded writes preserve it only for that repair; unrelated writes supersede it. Record/latch guarded errors even if upstream discards the returned error.
4. Clear only after successful full call, no guarded error, current epoch and compare-and-delete under a marker-admission fence. Late ordinary writes must either defeat the clear or establish a new marker before their mutation. Do not clear because MAC insertion returned, Connected arrived or bare AppStateSyncComplete was dispatched.
5. Failure, timeout, clear conflict or shutdown retains marker and appropriate health state. No unlimited retry, data truncation, key deletion or automatic phone unlink. Restart can retry after fixing the cause. Normal successful updates can conservatively retain a marker for next-start verification.

Gate storage-dependent later operations on startup recovery/fault health, not merely Connected. Pair success proves authentication/linking only; pending repair must not be misrepresented as completed contact sync.

### Contention and Caller Deadlines

FetchAppState locks a plain appStateSyncLock before its ctx-aware work. Do not implement the deadline as only passing ctx to that method. Before connecting a generation with pending repair, reject untagged app-state progress/MAC/bulk-snapshot calls for all collections immediately with an expected recovery-pending outcome, before SQL/HTTP/shared admission. Essential AppStateSyncKey writes/reads and current tagged repair remain permitted. This keeps ordinary automatic sync from holding the global mutex across a fetch before repair, without disabling key delivery. Creating a normal dirty marker alone is not a trigger to interrupt healthy sync.

Use one actual-call lease for owner-invoked FetchAppState calls, retained until that invocation returns even if caller timeout/retirement occurred. It does not claim to serialize every SDK-spawned protocol task. Select deadline/cancellation/result, invalidate the ticket on abandonment, keep the marker and never clear on late success. No replacement FetchAppState goroutine may bypass a held lease; tests distinguish caller completion from actual method return.

Use bounded/nonblocking result delivery and recheck deadline before selected success. The pin actually spawns missing-key requests with context.WithoutCancel(ctx), so early cancellation cannot suppress them and generation cancellation alone does not stop them. Drop the proposed custom tail-context/slot timer. Record the pin's default 75-second response wait, per-key 24-hour dedup and stop's Disconnect/clearResponseWaiters plus retryFrame's up-to-five-second connection wait, without claiming a ten-second or hard total tail bound. The old-generation guard still denies/cancels persistence after retirement regardless of caller ctx. Inactive repair tags reject protected app-state progress/clear but do not block necessary generation-valid key-request crypto/key delivery; those take fresh normal shared leases/deadlines. SDK tails remain documented upstream receive work, not owner-invoked FetchAppState slots or new full-resync attempts.

Record deferred ordinary collection requests in a bounded five-name bitset. After required recovery succeeds, release ordinary admission and replay coalesced demands incrementally through the same call slot; they are not extra full-resync retries. A failed replay waits for new notification/connection demand rather than an autonomous spin. Guarded-write faults during active use pause/cancel the generation; recovery proceeds after explicit restart with admission configured early. Transient missing-key failure keeps the marker and key-delivery path alive. The one-full-resync-per-collection/generation budget and all existing time/byte limits remain unchanged.

## Stop and Failure Contract

Register owner after store, so reverse cleanup is owner -> store -> lock. Stop request rejects windows/new attempts, clears QR, cancels refresh/repair/lifetime and callback admissions, removes handler/disconnects outside callbacks, and waits generation drain. Then shared store quiesces and pools close. On ten-second notification latch unsuccessful exit and keep waiting; use fresh cleanup contexts, not the expired deadline for later steps. Never advance from not-quiescent to lock release. One completion waiter prevents close retries leaking goroutines.

After quiescence, pool-close I/O errors remain unsuccessful but do not imply a still-admitted writer. Second signal/OS kill is explicitly unclean. A device mutation/repair failure during active use is surfaced and fail-stopped where necessary, not masked by an automatic reconnect. Expected stop cancellation is not an account/logout error.

## Diagnostics, Exception and Tests

One stderr slog bridge drops upstream format arguments at every level, including QR, keys, bodies and errors. Audit module/template treatment and preserve existing storage log contracts. Owned events use bounded reason codes and an opaque epoch, never account identifiers/QR/tickets. Emit coarse heap/goroutine samples at fixed one-minute debug cadence with no history; operator OS monitoring and a stop/reassess runbook are compensating controls, not prevention of upstream exhaustion.

E003-RX-01 excepts only recorded upstream receive bounds until its expiry/trigger. Tests must prove the non-excepted fake/session/QR/version/store/repair/stop contracts, plus zero-effect rejection, stale events, nested tx rollback, stable first-Save readiness and deferred deletion, marker/late-clear races, failure between every sibling state write and cleanup with held I/O. Negative platform claims require native tests. No real-account test or protocol patch is included in automated suites.
