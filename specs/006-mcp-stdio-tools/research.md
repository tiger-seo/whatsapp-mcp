# Research: MCP Chat and Contact Reads Over Stdio

**Date**: 2026-11-17, R6 extended 2026-11-18. Repository/upstream research and analysis remediation; no implementation, dependency modification or real-account action. R6 records the T001 store-isolation spike and the policy adopted in contracts/store-and-lifecycle.md; its numeric values are owner-approved inputs and measurements on one host, not verified bounds for every target.

## R1. Official SDK and Registration

**Decision**: Pin `github.com/modelcontextprotocol/go-sdk v1.8.0`. Use `mcp.NewServer`, lower-level `Server.AddTool` with explicit input/output schemas, `CallToolResult.StructuredContent` and explicit safe `TextContent`. Use public `jsonrpc.DecodeMessage`/`EncodeMessage` at the custom transport seam and `NewInMemoryTransports` for acceptance. Supply server name `whatsapp-mcp` and the existing build-info version, not a hard-coded historical release.

**Rationale**: D15 mandates this SDK. Stable v1.8.0 was published 2026-09-04 and requires Go 1.25, compatible with the repository's 1.27.4 toolchain. The low-level registration path keeps missing/null/explicit-zero semantics and safe rendering under application control. Validate both explicit schemas and output DTOs in tests and at the handler boundary; low-level AddTool must not be mistaken for automatic validation. Construct schemas with the SDK-supported representation rather than relying on description tags for defaults.

**Alternatives considered**: Generic `AddTool[In,Out]` validates and applies defaults but adds hidden output marshaling and is less direct for presence validation and pre-serialization accounting. Either API is valid generally; use one consistent explicit path here. Old v1.4.1 is historical reference, not a required pin. Do not adopt a second SDK, fork it or change whatsmeow.

**Evidence**: [version metadata](https://proxy.golang.org/github.com/modelcontextprotocol/go-sdk/@v/v1.8.0.info), [module manifest](https://proxy.golang.org/github.com/modelcontextprotocol/go-sdk/@v/v1.8.0.mod), [server.go](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/mcp/server.go), [transport.go](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/mcp/transport.go), [jsonrpc.go](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/jsonrpc/jsonrpc.go). Exact transitive module graph and vulnerability status must be checked when the dependency is added; a version's existence is not a security audit.

## R2. Admission Before SDK Dispatch

**Decision**: Implement the public SDK `Transport`/`Connection` seam, not MCP method handling. Enforce bytes/depth/envelope limits before returning a message from `Read`. Bound all request IDs, not only tools: string IDs at most 128 encoded bytes; numeric IDs only plain decimal integers in the exact float64-safe range -(2^53-1) through 2^53-1, checked lexically before SDK decoding. Hold four outstanding-request credits until the corresponding response finishes writing, including SDK-generated errors and cancellation before handler entry. Hold a separate one-tool credit through response completion; reject excess tool work without a store call. All control requests use the same outer accounting. Reject duplicate active IDs, batches and unsolicited responses; this server initiates no sampling, elicitation or other client RPC.

**Rationale**: `internal/jsonrpc2/conn.go` has an incoming-ID map and an unbounded handler queue. Receiving middleware runs after protocol decoding/admission, so a semaphore there cannot protect that queue. Incoming entries may be removed before response output completes; transport credits must outlive SDK bookkeeping. A bounded overload response may be written directly at this connection boundary, serialized with normal responses; it is not forwarded to the SDK or accumulated in another queue.

**Notification decision**: Forward only `notifications/initialized` once and well-formed cancellation notifications for outstanding IDs, at most one cancellation per ID. Ignore unknown notifications without reflecting their contents or retaining state. Forward notifications 1 through 1,024; the attempted 1,025th is not forwarded and stops the session with a secret-free diagnostic. This deliberately finite compatibility limit bounds SDK notification work even where middleware is bypassed; ordinary sessions normally send one initialization notification, while repeated cancellation-heavy clients eventually need a new session. Cancellation never starts a new request or grants authority. Reject malformed essential notifications. Explicitly disable tools listChanged and subscription capabilities/default handlers; reject `subscriptions/listen` before SDK dispatch. No retained subscription state or outbound list-change notifications are allowed.

**Error decision**: Prevalidate admitted method parameter shapes before SDK decoding where possible, and replace outbound SDK protocol error messages/data with fixed category-specific text before encoding/output. Never expose raw malformed params from SDK parameter-decode errors. Preserve ID/error code correlation without echoing values. Implement common connection guarding for production and for the server end of the official in-memory pair; sanitized handlers alone do not cover SDK-before-handler errors. Disable raw SDK logging/LoggingTransport or replace it with fixed safe categories. Correlation uses decoded ID values, not raw spelling, so escaped strings and -0/0 cannot bypass duplicate checks.

**Alternatives considered**: Stock `StdioTransport` only has a 16 MiB frame bound; handler/middleware-only admission arrives too late. Blocking all input when request credits fill would prevent cancellation. Unlimited error-response or notification queues simply move the exhaustion risk. A finite lifetime notification budget is intentionally simpler than proving completion of SDK preemptive cancellation goroutines.

**Evidence**: [internal/jsonrpc2/conn.go](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/internal/jsonrpc2/conn.go), [shared.go](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/mcp/shared.go), SDK transport source above. These files are implementation evidence for a pinned dependency, not an imported API.

## R3. Interruptible Session, Process-Lifetime OS Pumps

**Decision**: Use exactly one input pump and one output pump per command process, with fixed buffers/channels. The connection's stop signal independently interrupts its public `Read`/`Write`, including queue acquisition, without relying on closing inherited OS handles. On timeout/EOF/failure the session is permanently stopped; no replacement pump or session is started in that process. Pumps carry only bytes and completion signals, never owner/store references or callbacks. After actual handlers and account/storage work drain, normal process exit terminates any fixed OS-blocked pump.

**Rationale**: Go file deadlines work only for pollable handles; inherited Windows anonymous pipes cannot be assumed overlapped/pollable. A goroutine timeout is unsafe if replacement pumps accumulate, but two fixed process-lifetime goroutines are a finite resource. The application does not promise pump joins or in-process transport reuse. The SDK can write responses using a context that suppresses cancellation; connection-owned stop/deadline checks are therefore essential. Stop the connection before calling SDK session Close/Wait: Close alone waits for handlers and does not first cancel them. Confirm actual handler completion, not merely transport-return completion, before storage cleanup.

**Unix detail**: Handle SIGPIPE for the stdio command lifetime, including detached pump lifetime, so closed stdout/stderr yields an I/O error rather than abrupt process death before quiet-stop. Do not restore default SIGPIPE behavior while an output pump may still run. Test closed pipes in subprocesses on native platforms.

**Diagnostics decision (corrected for C1)**: Install SIGPIPE policy, the sink and failure latch before runShell. Keep one diagnostic pump but separate ordinary (16 x 4 KiB) and mandatory (16 x 1 KiB) queues. Successful-read/info/debug logs are best-effort; denied/failed request events, WARN/ERROR including history_incomplete/receive-loss, terminal faults and human refusal/failure diagnostics are mandatory. Fixed enum count/time accounting has at most 128 cells. Submission is synchronous only to bounded memory; producers never wait on OS I/O. The pump prioritizes mandatory events after its current write. Use one shared earliest-deadline timer: any mandatory queue overflow, invalid bounded record, sink failure or lack of full-write acknowledgment within 5 s latches diagnostic_delivery_failed and requests normal unsuccessful shutdown. Pending mandatory records at exit cannot be called delivered or discarded as ordinary logs. Preserve original loss/fault categories and exit 1 as observable fallback when channels cannot deliver; do not force marker changes or release ownership early. Ordinary drops may continue only while no mandatory obligation fails. Total OS pumps remain three, no retry/replacement pump or recursive logging, and no cleanup depends on flushing stderr. Complete OS-write acknowledgment is not durable audit/downstream retention.

**Alternatives considered**: Assuming `os.File.Close` unblocks every inherited stream is unsupported. Windows `CancelSynchronousIo` needs thread/handle-specific machinery and is not a universal immediate-cancellation guarantee. A reusable cross-platform pipe library or helper process is unnecessary for one process-lifetime session. Killing the process before account/store drain is forbidden.

**Evidence**: [Go file documentation/source](https://pkg.go.dev/os#File.SetDeadline), [Go program execution](https://go.dev/ref/spec#Program_execution), [SIGPIPE behavior](https://pkg.go.dev/os/signal#hdr-SIGPIPE), SDK conn/transport source; `cmd/whatsapp-mcp/lifecycle.go` logs before cancellation. Up to three blocked pumps including diagnostics are an explicit bounded process-lifetime detail, not an unbounded leak or claimed OS-I/O cancellation proof. A subprocess that does not exit after verified cleanup fails acceptance.

## R4. Output Bytes Are Independent of Store Row Budgets

**Decision**: Public typed DTOs only. Before marshaling a result, calculate an overflow-safe conservative encoded-size charge from every string, field, item and envelope. Permit at most 2 MiB structured JSON and 2 MiB ASCII-safe JSON text, and at most 8 MiB final JSON-RPC response, including both representations. Count actual emitted bytes too. Use the same semantic result for text and structured content; reject oversized results with `resource_limit`, never shorten a successful page. Only one tool response may be under construction/output at a time.

**Rationale**: Store `maxResultBytes = 32 MiB` counts fields, not escaped JSON. Control characters can expand sixfold before the text representation is encoded as another JSON string. Unchecked marshaling can allocate well before `Connection.Write` sees a frame. Preflight charges must cover that expansion and SDK copies; final connection checks are defense in depth, not the primary allocation control. The safe text renderer produces an ASCII JSON representation, escaping C0/C1, DEL and non-ASCII including direction controls; decoding it must yield the structured result unchanged. Preflight per-field escaping can overestimate and reject safely. No giant intermediate is permitted merely because it will be rejected afterward.

**Alternatives considered**: A 640 MiB response ceiling could cover some theoretical worst-case store pages but is an undesirable new default and still needs a proof. Blind `json.Marshal` followed by length checking is too late. Dropping latest messages or rows silently violates the spec. Returning a clear limit error and suggesting a smaller page or `include_last_message: false` is allowed.

**Evidence**: `internal/store/limits.go`, `queries.go` resultBudget; SDK `CallToolResult` and response marshaling path. Audit all DTO strings, invalid UTF-8 replacement, escaping, fixed metadata and request-ID contribution. The 2/2/8 MiB values are proposed fixed review bounds, not owner-approved compatibility measurements.

## R5. Store Query Alignment

**Decision**: Reuse the five read queries and local `resolveContact`; introduce no network contact/group lookup. Add `withLatest` to `GetChat` and update all internal callers/tests, avoiding a compatibility shim. Fold JIDs as well as query/name in chat search. Make contact search a literal folded substring across names and stored phone digits, not an implicitly normalized phone query; formatted identity normalization remains for contact-taking tools. Restrict returned contact identities to phone/LID domains. Keep grouping aliases before paging, phone-entry name preference, and folded chosen-name/JID contact ordering. Expand `ContactChats` membership to any stored chat with a matching sender, as FR-008 says, using `EXISTS` to avoid duplicates.

**Rationale**: Current `GetChat` always queries latest; throwing the field away still consumes work and can fail its budget. `SearchContacts` normalizes phone-looking queries, conflicting with literal FR-006, and excludes groups without restricting unsupported domains. `ContactChats` currently checks sender membership only for groups. Changing these precise paths follows the new explicit contract rather than assuming inherited implementation is the behavioral source. Existing tests that expect normalized search queries must be updated deliberately; no earlier MCP caller exists to preserve that behavior.

**Preserved details**: Exact direct lookup prefers phone chat, then mapped/unmapped LID; both actual rows may appear in plural contact chats. Latest ties use timestamp descending then message ID descending. Chat sorting places missing activity last and unnamed/name-quality-zero chats last. Phone normalization accepts 1-20 digits and documented punctuation; contact device suffixes are stripped, but `get_chat` rejects device-specific JIDs. Unknown mappings never invent a phone.

**Evidence**: `internal/store/queries.go:247-466`, `contacts.go:18-87`, `validate.go:38-79,138-198`, `contacts_test.go:40-55`. Queries use parameter binding and `instr`, not caller-built SQL identifiers.

## R6. Store Isolation and Actual Completion: Blocking Prerequisite

**Status/decision (2026-11-18)**: Policy specified, subject to the owner-judge design review: see "Candidate first-step mechanism and ceilings", "Owner decisions", "Candidate admission" and "Candidate WAL guard" below, adopted in contracts/store-and-lifecycle.md ("Isolation Policy"). The earlier assertion that one immediate shared-gate read establishes FR-017 stays withdrawn. One protocol tool credit and zero queued tool jobs remain. FR-017 and terminal ingest ErrBusy are unchanged. The paragraphs between this status and the candidate sections record the investigation in order; where they say "open" or "not established", the later sections supersede them.

**Pinned-driver findings**: `go.mod` pins modernc.org/sqlite **v1.61.0**. Static source inspection finds context cancellation/progress/interrupt handling, but the handler installed during stmt.query is removed when that call returns, whereas later rows.Next steps separately. Therefore cancellation during a later expensive Next cannot be assumed equivalent to initial query cancellation. Inspect/test the exact pinned paths, including driver/database/sql cleanup, before any actual completion claim. `sqlite.Limit(*sql.Conn, ...)` supplies particular connection limits, not a general per-connection heap or VM-step quota; connection/DB handles are private, and unsupported handle access is not a solution.

**Required admission result**: An atomic tool/ordinary policy protecting message writes and all guarded device operations, with no tool waiter, no speculative readmission ahead of ordinary work and written adversarial schedules. A separate tool class/private reader is a candidate, not an approved extra lease/connection: existing 16-active/64-waiting/four-reader totals still apply unless the owner explicitly approves a revised profile. Closing/accounting must cover all real work through actual return. Neither opportunistic TryAcquire nor mere process-loop priority proves this policy.

**Required query/resource result**: Bound source fields, actual scanned candidates, grouping/sort intermediates, Go memory, SQLite/cache allocations, temporary disk and WAL retention. Existing contact GROUP BY/order processes candidates before page LIMIT and is not accepted as bounded work merely because it returns 200 rows. Investigate indexed keyset batches with concrete total candidate/byte limits and bounded Go aggregation; return resource_limit rather than a partial page. Private caches/advisory cache_size and temp_store=FILE alone do not bound process-wide SQLite heap or temp disk. Do not lower process-wide hard_heap_limit to simulate tool-only isolation, increase budgets, or implicitly add a second database/process.

**Time semantics**: 5 s store (1 s before the design review of `68ce167`) and 10 s tool timers request cancellation; they do not assert completed work. T001 must establish supported actual termination/resource-release bounds for initial execution, Next, folding, connection acquisition and transaction close, with documented normal-OS/driver assumptions and control-failure behavior. No guessed grace time is a proof. A control failure latches unsuccessful normal shutdown with actual accounting/ownership retained; it does not authorize a replacement snapshot or automatic forced account kill.

**Preliminary native experiment (2026-11-17)**: With Go 1.27.4, Windows/amd64 and the pinned driver, a public `database/sql` transaction returned a first row, then entered a recursive aggregate in the next `rows.Next`; a registered scalar callback signaled that the aggregate had actually begun. Cancellation immediately after that signal did not make `Next` return until 2.476 s later; it returned `true` while `rows.Err()` was `context canceled`. The uncancelled comparison took 1.723 s. The same aggregate performed as an initial query returned a cancellation error 0.542 ms after cancellation. Rows close, transaction termination and a subsequent write were observed only after the operation returned. This synthetic query includes a Go callback in each aggregate row, so the timings are not a production-query bound or an isolated SQLite VM benchmark. It is a counterexample to assuming that the context request immediately drains a later step, not a proof that every possible bounded query is unsupported. Details and reproduction are in verification.md.

**Source mechanism**: In the pinned driver `stmt.go:287-299,340-360` installs the interruption watcher around the first step and removes it on return; `rows.go:107-123` performs subsequent steps without reinstalling it. `sqlite.go:80-139` shows the driver's internal interrupt/progress handling. The driver's exported `sqlite.Limit` (`sqlite.go:1363-1380`) limits SQLite categories, not general work or per-connection heap. The inspected source did not expose a supported API to extend that internal watcher over later iteration. This source explanation and a single observation do not exclude a separately bounded query design.

**Query strategy research, not a decision**: `internal/store/bench_test.go:310-351` asserts representative plans and the native `TestQueryPlans` run passed (verification.md). ListChats and ContactChats use ordered index scans; filtering and membership may require examining the full population before a page is found. GetChat and DirectChat use indexed point lookups but latest-message and contact-name values still need pre-materialization size controls. SearchContacts uses grouping and ordering temp B-trees before paging. Existing `temp_store(MEMORY)` and the 256 MiB process-wide hard heap limit (`internal/store/store.go:28-34`) mean intermediates can compete with writes; they are not per-tool isolation.

An indexed walk of unfiltered candidates, with continuation from the last **examined** key and explicit total candidate/byte/probe budgets, could bound work for chat lists. The mixed ascending/descending activity order and NULLs require correct continuation; `LIMIT` on matching rows is not a scan bound. Contact search could walk bounded contact entries and group aliases in bounded application state, then select a globally ordered page only after all relevant entries have been processed; exhaustion must return `resource_limit`, never a partial page. Offset up to 100,000 makes top-page and grouping state material. Neither approach has been shown to preserve all 006 semantics; a preliminary activity-order prototype is described below. Existing one-transaction snapshots preserve consistency but retain WAL; separate transactions would change snapshot semantics. A synthetic held-snapshot experiment confirms retention even with default autocheckpoint, not an operational growth bound (verification.md).

**Activity-keyset prototype**: A synthetic scratch implementation now splits the non-NULL walk into equal-timestamp/JID continuation and lower-timestamp queries, then walks the NULL partition by JID. Four batch sizes traversed 235 rows in exactly the same order as full SQL sorting. `EXPLAIN QUERY PLAN` initially showed the NULL continuation using only the expression prefix despite a `jid > ?` filter; explicitly adding `last_message_time IS NULL` led SQLite to report a JID range seek. This remains a small correctness/plan experiment, not a demonstrated resource bound: it does not cover pages, budgets, byte lengths, cancellation, mutation, alternate data distributions or all actual tool SQL. Exact plans and results are in verification.md. Contact grouping remains unprototyped.

**Focused paging follow-up**: A separate scratch model now compares activity-order JID-substring pages against SQL baseline for nine cases and asserts no partial returned page for three candidate-budget failures. It does not exercise the real store, folded names/JIDs, latest details or source-byte limits. Its budget check happens after `rows.Next`; consequently one extra SQLite step can occur before the candidate-budget error, and a page `LIMIT` and Go counter alone do not establish VM work/completion bounds. This is evidence for a possible paging algorithm, not approval of it or a total resource bound. See verification.md for exact fixture/cases.

**Budget-boundary follow-up**: The scratch paging model was revised to limit each SQL batch to the remaining candidate budget and return before calling `Next` again when that budget is spent. The 13-case run includes an exact-budget full page, which succeeds, and an incomplete exact-budget page, which conservatively returns an error without probing whether another row exists. This removes the previously observed additional returned-candidate step in this model, at the cost of possible `resource_limit` on a complete short final page. It does not limit VM steps, value sizes, query preparation, SQLite shared allocations or elapsed time; no production behavior or numeric budget has been approved. See verification.md.

**Admission candidate, source analysis only**: The current common gate (`internal/store/admit.go:57-115`) has a fast acquisition path that does not check existing waiters; ordinary store paths and guarded device calls share it (`ops.go:33-103`, `device.go:280-368`). A check-then-tool-grant outside a single coordinated lock can race an ordinary arrival. A candidate coordinated gate would register ordinary arrivals and grant under the same lock, stop new tool grants when ordinary work is pending/active, give ordinary waiters explicit priority, admit no queued tool and retain the tool's existing-budget lease until actual return. Close and grant/accounting need a common linearization point; nested device calls must reuse their outer lease. This conservative policy can starve tools, and even a correct reservation cannot preempt a tool already holding SQLite resources or a WAL snapshot. No implementation, deterministic schedule test or isolation guarantee follows from this proposal.

**Focused concurrent cancellation experiment**: A held later `Next` in a synthetic two-connection WAL database remained active after cancellation while 1,000 writes completed. The held snapshot prevented 336 WAL frames from being checkpointed; after releasing the deliberately blocked scalar callback and actual transaction return, truncation succeeded. This demonstrates the interaction in a controlled synthetic model, not an ingest failure or production-folding timing. See verification.md. The public `sqlite.DBStatus` API (`modernc.org/sqlite@v1.61.0/dbstatus.go:13-34,58-77`) offers counters, not an enforced per-tool quota; no supported public later-step interruption/progress or per-connection VM-work control was found in the pinned driver.

**Admission counterexample, conditional model rather than runtime evidence**: Suppose a tool is admitted when idle and remains active after an ordinary arrival requests cancellation. If 15 ordinary operations occupy the remaining active slots and 64 ordinary operations wait, the next ingest write encounters the current waiter overflow `ErrBusy` (`internal/store/admit.go:60-85`). Without the tool, the same initial ordinary arrivals can instead occupy 16 active slots and 63 waiter slots, leaving that ingest write as waiter 64; a later ordinary release can let it succeed. A priority policy prevents repeated tool barging but cannot reclaim the active lease while real SQL is running. This refutes unconditional baseline-equivalence for that schedule under the stated overflow rules; FR-017 describes flood-induced ingest failure and does not unambiguously require universal baseline-equivalence, so the counterexample does not by itself prove the feature impossible.

**Prerequisite decision status**: The experiments establish that context cancellation alone, result/candidate limits alone, and priority admission alone are insufficient for the documented T001 proof. A fully supported mechanism preserving all required resource and completion guarantees has not been established, but impossibility under every possible design has not been proved. Candidate owner decisions, none approved here: (1) continue a narrowly scoped pinned-driver query redesign, possibly one-row context-scoped calls plus bounded source fields, while separately proving heap/WAL/admission and accepting possible tool starvation; (2) authorize evaluation of an appropriate driver change exposing supported interrupt/work controls, with independent shared-resource and I/O analysis; (3) reconsider isolation architecture or explicitly revise the protection/resource profile through the applicable constitutional and owner-review process. A driver change, extra process/database, increased budgets, exception, or retry of terminal ingest errors is not authorized by this list. Keep T001 blocked and do not treat unverified alternatives as a solution.

**Candidate first-step mechanism and ceilings (2026-11-17/18, scratch evidence in verification.md, not approved)**: Each multi-row read is wrapped as one aggregate row so all SQLite work runs in the first step, where the pinned driver's interrupt watcher is installed; the tool reader opens and closes a pooled connection per read and checks its context after success. `list_chats` and `get_contact_chats` walk at most C = 100,200 chats in index order (exact for full pages and for stores of at most C chats, otherwise `resource_limit`); the outer page must order by an aliased walk column or SQLite sorts offset+limit rows. `search_contacts` prechecks entries (≤ 100,000), chosen-name bytes (≤ 4 MiB), all-field bytes (≤ 16 MiB) and field length (≤ 1 KiB) before grouping; measured worst case 23.6 MB SQLite heap and 2.3 s, sized against a proposed 32 MiB tool heap share. `octet_length` guards source values before folding or materialisation.

**Owner decisions (2026-11-18)**: 32 MiB tool heap share, offset cap 100,000 kept, conservative `resource_limit` accepted, capacity-neutral admission with one extra ordinary waiter place while a tool holds a slot.

**Candidate admission (experiment 2, model evidence)**: one mutex decides both classes. A tool read is admitted only when no ordinary operation waits and a slot and a reader are free; it never queues; it is cancelled when an ordinary operation must wait for a slot or a fourth ordinary read needs its reader; its slot and reader stay accounted until actual release; the ordinary waiter cap is 65 while it holds a slot. In the scratch model an ordinary `ErrBusy` occurs only with 80 ordinary operations in flight, as without tools, and a tool delays ordinary work by at most its release latency. That latency is load-bearing: a tool that does not return within the 5 s admission wait turns into an ordinary `ErrBusy`.

**Design review of `68ce167` and amendments (2026-11-18)**: CONCERNS. The owner chose a 5 s store timer (re-measured on the real store: contact search at the ceilings 1.6–2.7 s, chat walks ≤ 357 ms, 0 of 90 reads timed out), a recovery TRUNCATE checkpoint for an oversized -wal without writes (0.70–0.96 s for 210–241 MB), and accepted the low-disk refusal. Reader accounting now names every gated reader-pool user; the 128 MiB check runs after each gated write. Evidence in verification.md.

**Candidate WAL guard (experiment 4, real store)**: heap is not binding (24.3 MB with ingest), WAL retention is: back-to-back tool snapshots let the WAL grow with all ingest (603–757 MB in 20 s). Proposed: admit a tool read only while the -wal file is at most `walLimitBytes` (64 MiB; a larger file means no reset since the last growth), cancel it when the file passes 2 × `walLimitBytes`, and admit it only while the disk guard is not refusing and the last free-space measurement is at least `diskResume` + 2 × `walLimitBytes` (640 MiB), so the tool-attributable WAL (at most about 2 × 64 MiB plus one batch above the normal 64 MiB) cannot by itself bring free space below the 256 MiB reserve. The free-space condition is reasoning, not tested; the measurement is cached up to 30 s. A per-read byte budget alone was measured ineffective (chained snapshots). Not verified: the real gate, device operations under load, a near-full disk, other native targets.

**Exit criteria**: Synthetic scratch spike, exact pinned source/control argument and query plans, fixed resource ceilings and adversarial/native evidence are recorded; unsupported or unverified control combinations remain blocked. Stress results accompany the mechanism argument, not replace it. If current architecture/pins cannot support the required isolation/completion controls, stop for an explicit owner prerequisite decision and renewed design; do not start T002-T042 or declare PASS.

**Evidence**: `go.mod:21`; `internal/store/admit.go`, `ops.go`, `device.go`, `contacts.go:34-63`, `store.go:26-34`; pinned `modernc.org/sqlite@v1.61.0/{sqlite,stmt,rows,conn}.go`; `docs/backlog/005-store-busy-stops-ingest.md`. The global SQLite heap and WAL risk are inherited; this feature must not introduce a read path that defeats their required write availability.

## R7. Stdio-Only Lifecycle and Terminal Faults

**Decision**: Replace only `runStdio`'s input-discard goroutine with the MCP session. Keep `runShell` prerequisites and `attachOwner`; the latter publishes the generation and starts saved-session connection asynchronously. Start MCP after successful attachment without waiting for WhatsApp connectivity. Register the MCP drain step after owner registration, since cleanup runs in reverse order. On cancellation stop admission and cancel requests promptly; actual account retirement may run concurrently, but store close/lock release wait for both.

**Device faults**: Keep `Owner.Terminal()` as the existing ingest-failure signal because `serve` uses it too. Subscribe in stdio only, then immediately recheck latched `Health().StorageFault`; callbacks only wake a capacity-one channel, never call owner methods under the owner's lock. Check health outside callbacks and again after owner drain to catch EOF/fault races. Device faults exit 1 with a device-specific diagnostic; preserve existing ingest failure behavior in both shells. No device-only change to serve.

**Evidence**: `cmd/whatsapp-mcp/commands.go:483-618`, `lifecycle.go:77-95,137-177`, `internal/wa/owner.go:198-365,466-481,541-620,792-800`, `client.go:94-110`, `owner_terminal_test.go:67-81`. Existing scripted owner has an already-closed Done channel; extend or replace that test rig where actual drain ordering is asserted. Reuse `ingest_cmd_test.go`, `lifecycle_test.go`, `pair_test.go` seams. Never reorder feature 004's network fence and device barrier or clear the marker from MCP code.

**Alternatives considered**: Closing Terminal on all device faults would silently change serve. Starting MCP before store/run-marker validation bypasses established startup safety. Waiting for Connected prevents useful local reads during ordinary offline operation.

**Decision**: Treat the owner's all-data local-read decision as the authorization policy, not a prompt-injection solution. No send/pair/QR tool exists. F03 protections remain inherited; F09 protocol/output bounds are proposed; store isolation/completion follows R6's policy (contracts/store-and-lifecycle.md), subject to design review and implementation evidence, not timer/flood evidence alone. Mandatory loss/audit reporting uses R3's latch/failed-shutdown path, not ordinary discardable logs. F15 exact dependency/integrity/vulnerability/build gates remain. No exception, owner verdict or compliance claim; HTTP/webhook/release-wide work stays with 010/011/012.

**Verification approach**: Official SDK in-memory acceptance for all parameters/results/errors; native subprocess tests for process-lifetime pumps and SIGPIPE; one-snapshot/no-wait/flood tests with synthetic ingest and device writes; actual encoded-byte and memory measurement; unchanged quiet-stop/serve regression tests. Record commands/counts/exits/platform skips in verification.md. Owner reviews follow task generation and implementation, not this research step. No CGO race run is assumed authorized by the old feature's exception.

**Evidence**: Constitution 3.0.0 I-X, `docs/security-review.md` F01-F16, spec Security, source section 8.11 owner decisions, CI workflow and `AGENTS.md` commands. New resource values are design proposals subject to review, never an implicit waiver of mandatory controls.
