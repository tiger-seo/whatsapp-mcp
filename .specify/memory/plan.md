## Summary

The `whatsapp-mcp` binary skeleton provides build identification, five CLI entry points, layered startup configuration, structured stderr logging, exclusive data-directory ownership and signal/EOF shutdown. Only `version` had its final behavior at this baseline; the other entry points established the startup, streams and shutdown wiring. [Source: .specify/archive/001-binary-skeleton/plan.md -> "Create the `whatsapp-mcp` binary"]

The feature 003 historical baseline adds a connection owner, terminal pairing, offline status, guarded device persistence and fail-closed offline recovery. Its plan contains design obligations and its verification records partial and completed evidence; neither an unrun control nor an earlier design alone establishes implementation. ## Routing and Lifecycle

- One `flag.FlagSet` per command. Dispatch on the first argument; only top-level `-h`/`--help` is accepted before a command. Flags go after the command, accept either dash form and either space or `=`, and there are no positional arguments. Help lists the relevant environment variables and defaults. [Source: .specify/archive/001-binary-skeleton/research.md -> R1] [Source: .specify/archive/001-binary-skeleton/contracts/cli.md -> "Flags go after the command"]
- `version` bypasses configuration, environment, directory and lock and prints the version, commit, date, Go runtime and target in that order. `dev` is independent of the module version; commit/date use injected values, then VCS metadata, then `unknown`; append `-dirty` where applicable. [Source: .specify/archive/001-binary-skeleton/contracts/cli.md -> "On stdout, with one field per line"] [Source: .specify/archive/001-binary-skeleton/research.md -> R10]
- Other commands parse flags, load and validate config, initialize logging, and emit warnings/debug config. `stdio`, `serve` and `pair` prepare the directory and take the lock before running the command body; `status` uses the separate inspection path below. Exit 0 for success/help/clean stop, 1 for runtime refusal, forced stop or general failure, 2 for usage or invalid configuration. [Source: .specify/archive/001-binary-skeleton/plan.md -> "Startup sequence"] [Source: .specify/archive/001-binary-skeleton/research.md -> R11] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/cli.md -> "Shared Rules"]
- Install signal handling before configuration for long-running commands. First signal cancels work; only `stdio` watches stdin, and EOF/read error also cancels the skeleton. Register each named cleanup as its resource is acquired, run steps in reverse, log errors and keep running cleanup. Second signal exits 1 immediately; at the skeleton's 10 s deadline log the pending step and exit 1. Unix uses SIGINT/SIGTERM; Windows console Ctrl+C/Ctrl+Break arrive as interrupt, and console close/logoff/shutdown as SIGTERM. [Source: .specify/archive/001-binary-skeleton/research.md -> R8] [Source: .specify/archive/001-binary-skeleton/research.md -> R9] [Source: .specify/archive/001-binary-skeleton/data-model.md -> "Run lifecycle (`cmd/whatsapp-mcp`)"]

Writable storage wiring runs after directory preparation and the lock: `stdio` and `serve` register store close before lock release, and `pair` closes before returning. Store refusals are runtime errors (exit 1) with safe stderr diagnostics. [Source: .specify/archive/002-sqlite-storage/contracts/startup-and-events.md -> "Commands"] [Source: .specify/archive/002-sqlite-storage/research.md -> R13] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/cli.md -> "Shared Rules"]

Feature 003 replaces those skeleton command behaviors: `status` inspects the committed view offline under appropriate ownership, never connects or migrates, and missing storage creates nothing; unsafe or legacy-unknown state reports recovery required. `pair` uses one explicitly requested QR window; durable identity and Connected are needed for linking, and an unresolved attempt requires offline recovery. Shells do not implicitly pair. These are historical feature 003 contracts, not assertions about later transports. [Source: .specify/archive/003-whatsapp-pairing-status/contracts/cli.md -> "status"] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/cli.md -> "pair"] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/cli.md -> "stdio and serve in Feature 003"]

Feature 003's owner holds a single generation and connection attempt, arms the unsafe marker before account work, and retains it after any production Connect attempt. Recovery is offline and interactive, with separate phone verification, any unlink, local removal and later pairing authorizations; a missing local identity does not prove no phone-side link. Deny automatic reconnect by default; the owner-approved historical exception permits one same-generation post-pair 515 reconnect for `pair` only, with the recorded residual risk and conditions, not for the shells. [Source: .specify/archive/003-whatsapp-pairing-status/contracts/connection-owner.md -> "Protocol Adapter and State"] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/cli.md -> "pair"] [Source: .specify/archive/003-whatsapp-pairing-status/verification.md -> "T077 Residual Risk Corrected - 2026-11-07 (owner re-confirmation given)"]

A second signal is an explicitly unclean forced exit. [Source: .specify/archive/003-whatsapp-pairing-status/contracts/connection-owner.md -> "Stop and Failure Contract"]

## Configuration and Diagnostics

- One registry drives flags, help, environment lookup, validation and debug output. Resolve the absolute data directory first from flag, environment or `os.UserConfigDir()` plus `whatsapp-mcp`; then read optional TOML and resolve other settings by flag, environment, file, default. Clean absolute overrides; reject relative paths. Join validation errors before making changes. [Source: .specify/archive/001-binary-skeleton/research.md -> R3] [Source: .specify/archive/001-binary-skeleton/contracts/configuration.md -> "Settings (feature 001)"]
- Use a single environment snapshot; names are case-insensitive on Windows, exact elsewhere, with empty values treated as unset and one warning per unknown prefixed name. Old names, including `LOG_LEVEL`, are silently ignored. [Source: .specify/archive/001-binary-skeleton/research.md -> R4]
- Decode TOML to `map[string]any` and use `unstable.Parser` for top-level key line numbers; parser-supplied text unmarshaling is not the validation layer. Allow an empty file, reject unsupported keys/types and `data_dir`, and enforce the 1 MiB limit while reading (one extra byte detects oversize). [Source: .specify/archive/001-binary-skeleton/research.md -> R2] [Source: .specify/archive/001-binary-skeleton/contracts/configuration.md -> "It is at most 1 MiB"]
- Refuse existing non-private directories with a remedy, never silently repair. Use Unix mode 0700 for the new data directory or a protected Windows ACL for the current user, SYSTEM and Administrators. `config.toml` and the lock must be regular single-link files; open without following links and inspect the open handle. New lock: Unix mode 0600 or the private directory's ACL on Windows. The feature records limits concerning ancestor trust and effective-access testing. [Source: .specify/archive/001-binary-skeleton/contracts/configuration.md -> "An existing data directory"] [Source: .specify/archive/001-binary-skeleton/contracts/configuration.md -> "Files inside it"] [Source: .specify/archive/001-binary-skeleton/verification.md -> "Remaining risks"]
- Use one `slog` text logger on stderr, filtered by the configured level. Print pre-logger errors on stderr, escape terminal controls and show the origin, setting and remedy. Mask secrets in values and parser reasons, including TOML syntax diagnostics in or after a secret value. [Source: .specify/archive/001-binary-skeleton/research.md -> R7] [Source: .specify/archive/001-binary-skeleton/contracts/cli.md -> "Every message starts with"] [Source: .specify/archive/001-binary-skeleton/contracts/configuration.md -> "Each error names the setting or key"]
- Use nonblocking `TryLock`. Read at most 32 bytes of PID text from offset 1; byte 0 is reserved because Windows locks it mandatorily, unlike Unix advisory locking. Write via a second handle, truncate under lock on release, and do not delete the file, to avoid racing a new holder. Ignore stale contents; report unknown when the PID cannot be read or parsed. [Source: .specify/archive/001-binary-skeleton/research.md -> R6]

The store adds no configuration setting. Events use the process logger with UTC time, stable operation and outcome fields, and version information where relevant. Upstream SQL-store logging forwards level, module and format, not arguments. [Source: .specify/archive/002-sqlite-storage/plan.md -> "Constraints"] [Source: .specify/archive/002-sqlite-storage/research.md -> R12] [Source: .specify/archive/002-sqlite-storage/research.md -> R3]

Feature 003 keeps fixed limits, not new settings: a 30-second attempt watchdog separate from generation lifetime, discovery at 15 seconds and 1 MiB consumed, QR at 4 KiB and at most 60 seconds, and app-state HTTP at 10 seconds and 16 MiB. The historical desired three five-second retries are conditional on safety proof, not a claim that retries are enabled. Discovery uses verified HTTPS, rejects redirects and incomplete bodies, and preserves the previous version on failure; handshake payloads clone a coherent version without mutating globals. [Source: .specify/archive/003-whatsapp-pairing-status/plan.md -> "Performance Goals"] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/connection-owner.md -> "Versions and Discovery"] [Source: .specify/archive/003-whatsapp-pairing-status/verification.md -> "Mandatory Compensating Controls"]

## Storage Design

- Open with the `sqlite` dialect, foreign keys, WAL, a 5 s busy timeout and immediate writes. Use one write connection and four read connections, with bounded admission and the earlier of the caller's and operation's deadlines. Distinguish an indeterminate commit from a confirmed outcome. [Source: .specify/archive/002-sqlite-storage/research.md -> R1] [Source: .specify/archive/002-sqlite-storage/research.md -> R2] [Source: .specify/archive/002-sqlite-storage/research.md -> R9]
- Before any writable connection, validate existing artifacts and inspect the committed view of the main DB plus valid WAL commits through the read-only filesystem VFS. Check both independent versions before the pinned device upgrade; then apply embedded numbered message migrations. Each step owns its transaction and version record; later failure cannot undo already committed steps. [Source: .specify/archive/002-sqlite-storage/research.md -> R4] [Source: .specify/archive/002-sqlite-storage/research.md -> R3] [Source: .specify/archive/002-sqlite-storage/research.md -> R5]
- Create the main database privately; require strict Unix mode and macOS ACL checks or the approved Windows DACL. Validate actual file identity around startup and refuse unsafe artifacts without repairing them. Temporary data is kept in memory. [Source: .specify/archive/002-sqlite-storage/research.md -> R6] [Source: .specify/archive/002-sqlite-storage/spec.md -> FR-040]
- Preserve original text; search pre-folded, NFC-normalized columns with literal `instr`. Store times as UTC Unix milliseconds. Validate JIDs, opaque IDs, metadata and field limits before SQL. Resolve phone and LID identities through the device map; use ordered, independently indexed `UNION ALL` branches instead of a combined `OR`, and per-chat indexed existence probes for contact chats. The fallback direct-chat sender name uses the sender's exact JID, not its counterpart's chat. [Source: .specify/archive/002-sqlite-storage/research.md -> R7] [Source: .specify/archive/002-sqlite-storage/research.md -> R8] [Source: .specify/archive/002-sqlite-storage/research.md -> R11] [Source: .specify/archive/002-sqlite-storage/research.md -> R15] [Source: .specify/archive/002-sqlite-storage/verification.md -> "Owner decisions"]
- Enforce the 256 MiB process-wide SQLite heap limit with memory statistics enabled, separate from Go's heap. Check a free-space reserve before admitted store writes and resume only after the recovery threshold; keep automatic checkpoints and bound long readers. Failure does not delete keys, messages, journals or backups. [Source: .specify/archive/002-sqlite-storage/research.md -> R16] [Source: .specify/archive/002-sqlite-storage/research.md -> R10] [Source: .specify/archive/002-sqlite-storage/spec.md -> FR-045]

- Feature 003's guarded device interfaces share admission, disk and operation limits, retain stable guards across first save, reject unbounded exports and drain admitted work before closing. Nested compatible transactions reuse the admission and transaction context. Repair markers precede protected writes; ticket/revision fencing prevents late or superseded work from clearing uncertainty. Whole app-state sync is not one transaction and recovery never deletes chats or keys as a shortcut. [Source: .specify/archive/003-whatsapp-pairing-status/contracts/connection-owner.md -> "Device Store API and Admission"] [Source: .specify/archive/003-whatsapp-pairing-status/contracts/connection-owner.md -> "Durable Recovery Protocol"]
- The schema-3 unsafe marker and transferred repair needs are durable recovery barriers, not evidence that detached upstream handlers have joined. Use the required writer synchronization and fail closed when it cannot be established; process-kill tests do not prove power-loss survival or Darwin hardware flush. [Source: .specify/archive/003-whatsapp-pairing-status/plan.md -> "Unsafe-Run Barrier And Offline Recovery"] [Source: .specify/archive/003-whatsapp-pairing-status/verification.md -> "CI Platform Evidence for T068-T073 - 2026-11-06"]
